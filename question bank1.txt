NOT A SOLUTION KEY. No claim that the listed bugs exist in the user's own code.

EVIDENCE KEY
PATCH: a primary source-level change explains the particular failure.
REPORT: a contemporary developer or user reports the behavior; not automatically reproduced or fixed.
DISPUTED: an archival complaint is countered or the cause remains unsettled.
COURSE/RESEARCH: an academic or teaching problem, not a company production bug.
DERIVED: new practice counterexample inspired by historical failure modes.
CANDIDATE: claimed assessment from candidate account; not authenticated by employer.
PUBLIC: officially published challenge/workshop, not necessarily a hiring assignment.
UNVERIFIED: promising trail, exact underlying document requires further confirmation.

For every question: (1) read the source body and replies, (2) trace the example using numbers, (3) write expected outputs before code, (4) build deterministic tests, (5) implement a slow reference, (6) run relevant sanitizers, and (7) only then benchmark.

PART A: HISTORICAL THREADING, MEMORY, AND FIX SESSION FAILURES

01. Writer starvation under continuous readers [REPORT, Boost, 2008]
Input: 4 reader threads repeatedly query shared order data; 1 writer adds 1,000 orders. The April 2008 archive reports a particular 2-reader/1-writer benchmark with shared_mutex mean writer wait of about 760 microseconds versus about 7.108 microseconds for pthreads-win32. A separate September post reports waits exceeding 20 seconds under a different workload.
Tasks: Identify whether readers can overtake a queued writer. Measure writer maximum, p99 and mean waits separately. Repeat 30 times and record whether every write completes. Do not extrapolate performance to all C++ shared mutexes.
Sources:
https://lists.boost.org/archives/list/boost%40lists.boost.org/message/PY2JLUZCY4VSDDPP3LQY3HLJNAK2GBDL/
https://lists.boost.org/archives/list/boost-users%40lists.boost.org/message/HCCXEBYBWPHDKVSMGG4AZUDCPTKKNKGZ/

02. Waiting writers deadlock despite no active owner [REPORT, Boost 1.33, 2005]
Input: 10 threads acquire reader/writer locks in 1,000 iterations; the recorded condition is waiting threads with no active lock owner.
Tasks: Instrument reader count, writer flag and queued waiters. Contrast alleged Boost 1.33 behavior with earlier 1.32 under equivalent conditions. Find the original discussion and code before asserting a library bug.
Source trail: Boost shared_mutex mailing-list discussions, August 2005. Direct thread URL not reverified here.

03. QuickFIX suppresses a second, necessary resend [REPORT with developer reply, January 2006]
Original trace: expected 197648, got 197650, requested resend from 197648; recovered via SequenceReset to 197651. Later expected 216250, got 216251. The prior resend remained marked outstanding, suppressing the new request.
Tasks: Replay two disjoint gaps. Identify the exact transition that clears the outstanding resend range. Check whether application messages stop while the TCP session appears connected. Do not supply a patch before proving that transition.
Primary thread (includes original report and reply):
https://sourceforge.net/p/quickfix/mailman/quickfix-developers/thread/989aceac0601031239o13fc16b2l992c95d08f7c0c1f%40mail.gmail.com/

04. Condition-variable waiter starves although another worker progresses [REPORT, 1996]
Input: workers A and B wait; B repeatedly reacquires mutex ahead of A over 100 producer notifications.
Tasks: Distinguish a condition becoming true from FIFO fairness. Does signal transfer mutex ownership? Log notify order, wakeup order and actual work claim order separately.
Source trail: comp.programming.threads, June 1996; exact messages not reverified in this pass.

05. TCP retransmission seems stalled for 120 seconds [DISPUTED, Linux 2.0.x, May 1997]
Input: temporarily interrupt ACKs on a TCP connection while tracing every sent segment and ACK.
Tasks: Distinguish legitimate retransmission backoff/Karn's algorithm from a timer defect. Compare the reporter's claim against the response that did not reproduce the complete stall. Do not label normal exponential backoff a kernel bug.
Source trail: Linux-kernel May 1997 TCP retransmission discussion; original replies require follow-up.

06. Many short-lived connections accompany server freezes [REPORT, Linux 2.2.x, May 1999]
Input: create 10,000 short connections; inspect TIME_WAIT, FD count, port availability and CPU time.
Tasks: Which observation proves actual failure? Why does a large TIME_WAIT population not itself prove a defect? Correlate failures with socket/resource counters.
Source trail: Linux-kernel May 1999 Linux 2.2.7/2.2.9 connection-churn report.

07. Notified condition-variable thread incorrectly assumes mutex ownership [REPORT, 2001]
Input: three consumers wait, producer notifies one, then producer or another consumer acquires the lock first.
Tasks: Check predicate in a loop. Prove how another worker can consume an event before the notified worker runs. Separate signaling and lock acquisition.
Source trail: David Butenhof, comp.programming.threads, January 2001.

08. Worker thread launches before its mutex/condition-variable members are constructed [CODE-DERIVED, 2004]
Input: declare class members in the order worker, mutex, condition_variable, running; launch worker from constructor.
Tasks: Derive C++ member initialization order; identify what may be accessed before initialization. Test 10,000 immediate constructions/destructions and inspect races on running.
Source trail: Boost user's reported code, June 2004; primary post not re-opened here.

09. Notify occurs between unlock and starting to wait [REPORT, 2005-06]
Input: consumer sees empty queue and is paused between dropping mutex and blocking; producer inserts 1 item and notifies.
Tasks: Why can sleeping without a predicate loop lose progress? How does the real condition-variable wait avoid an unlock-to-sleep race? Force the interleaving with a barrier.
Source trail: Boost condition-variable threads, 2005-2006, including implementation objections. Exact patch unverified here.

PART B: SOCKETS, UDP, TCP, AND PACKET SCHEDULING

17. poll(POLLOUT) followed by send(EAGAIN) [PATCH REPORT, AF_UNIX datagrams, June 2008]
Input: one slow Unix datagram receiver and four fast nonblocking senders.
Tasks: Compare write-readiness notifications with actual send attempts; determine how receiver-queue saturation can cause an EAGAIN and repeated fruitless wakeups. Count failed sends and CPU cycles.

18. UDP packets dropped but sk_drops not incremented [PATCH REPORT, Feb 2009]

Input: gradually increase packet input until software can no longer forward work. Measure delivered packets rather than interrupts handled. Published setup showed severe overload collapse; individual measurements are platform-specific.
Tasks: Plot offered load, completed output, CPU and interrupt handling. Can 100% busy CPU mean zero useful output? Reproduce a scheduler-starvation analogue in a synthetic feed-handler pipeline.

25. Receive livelock optimization still starves output stage [ORIGINAL RESEARCH, 1996]
Input: producer injects data indefinitely; receiver processes in batches of 10, 100, then unbounded items; output stage has 200 queued items.
Tasks: Why is reducing interrupts insufficient if the receiver monopolizes execution? Measure delivered output and worker scheduling fairness, not just input handling throughput.
